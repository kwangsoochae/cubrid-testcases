# Cases whose expected answer is what an operator gives in SQL, where the PL engine gives
# something else for the same operator.
#
# The manual has the operators of a procedure body behave the way SQL's do
# (pl/plcsql_overview.rst, "Operators and Functions"), and where the PL engine departs from
# that the answer follows SQL (2026-09-24 decision). The test for admitting one is that plain
# SQL, outside any procedure, gives what the answer now shows:
#
#   LIKE     'abc' like 'a.c' is false and '(x' like '(' is false - the PL engine builds a
#            Java regular expression from the pattern without escaping . or (, so it matches
#            the first and fails on the second
#   << >>    1 << -1 is 0 and -1 >> 2 is 4611686018427387903 - the PL engine shifts as Java
#            does, by the count mod 64 and with >> keeping the sign
#   & | ^    'a' & NULL is NULL - the PL engine turns each operand into a Long first, so a
#            string fails before NULL is seen
#
# The answers were taken from a strict round, so each is what the body gives when it is run
# by the server and nothing else.
