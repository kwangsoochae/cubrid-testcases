# Cases whose expected answer is what the server's own executor does, which the PL engine
# does not do.
#
# This is a different reason from engine_wording_excluded_from_pl_engine_run.txt, and the two
# are kept apart so that each list can say what is true of everything in it. That one holds
# cases differing in the error sentence and nothing else. These differ in more than the
# sentence: an exception is raised where none was, or a different one is, or a different
# SQLCODE comes back.
#
# The test for admitting one is that the ENGINE agrees with the answer. Every case here was
# measured by writing the same expression in plain SQL, outside any procedure, and the server
# answered what this answer now holds - so the PL engine is the one differing from the engine
# it runs against, and pinning its result would pin the disagreement.
#
#   INT_MIN / -1, BIGINT_MIN / -1    plain SQL: Overflow occurred in division context.
#                                    PL engine: no exception, the wrapped value
#   numeric 1.00 / 0.00              plain SQL: Attempt to divide by zero.
#                                    PL engine: SQLCODE 4, internal server error
#   double 1.0 / 1e-320              plain SQL: Attempt to divide by zero.
#                                    PL engine: SQLCODE 8, a division overflow
#
# Two more were added the same way. Both are a system parameter the engine obeys and the PL
# engine does not, so the answer moves further than a sentence: one of the two settings stops
# raising at all.
#
#   allow_truncated_string=yes       plain SQL: 'abc'
#                                    PL engine: SQLCODE 8, the string does not fit
#   return_null_on_function_errors   plain SQL: NULL for zero date + 1 when it is yes,
#     =yes                           Attempt to use 'zero date'. when it is no
#                                    PL engine: SQLCODE 8 under either setting
#
# The case files said this was coming. Each carries a note that its answer pinned the behaviour
# of the day rather than the wanted one, and that a native executor was expected to change it.
#
# 01_03_06-10 differs only in the sentence and would pass the other list's test. It is here
# because the five were re-blessed together, in one measurement of one suite, and splitting the
# record by a hair's breadth would make both lists harder to read than keeping the work whole.
#
# One more was re-blessed later on its own (the COERCIBILITY PR) and is written here after the
# fact. Nothing is raised on either side; the value differs, and plain SQL gives the engine's.
#
#   COERCIBILITY (USER ())           plain SQL: 7
#                                    PL engine: 11 - it computes USER () in Java and hands over a
#                                    string, whose coercibility is not that of USER ()
#
# Two more are built-in functions answering differently in a body run by the PL engine. Plain
# SQL gives what the engine gives. Why the PL engine differs is not traced here.
#
#   FIELD ('123', 1, 12, 123.0, 1234, 12345)       plain SQL: 0      PL engine: 3
#   FORMAT (-876543210987654321.0987..., 4)       plain SQL: -876,543,210,987,654,321.0988
#                                                 PL engine: -876,543,210,987,654,300.0000
#
# Two more hand a SET, a MULTISET or a LIST to a CHAR or VARCHAR parameter. The PL engine takes
# it as the string {a, b, c}; the engine raises, and so does plain SQL.
#
#   cast ({'a','b','c'} as varchar)   plain SQL: Casting {'a', 'b', 'c'} to type varchar is not supported.
#                                     engine:    Cannot coerce value of domain "set" to domain "character varying".
#                                     PL engine: {a, b, c}
#
# The floating-point lines in the same two cases differ the way the ones in
# engine_notation_excluded_from_pl_engine_run.txt do.
#
# A line is the case file's name, without any directory - the same shape the other list uses.
#
